# UI / 菜单文本清点

> 清点时间：2026-10-19。工具：`scripts/exe-ui-strings.fsx`（提取）+ `scratch/crosscheck.fsx`（对账）。
> 原始数据：`work/inventory/exe-ui-strings.json`、`docs/data/steam-achievements.ja.txt`（用户提供的 Steam 页面文本）。

## 1. 结论（一句话）

**`Getsuei.exe` 里除 Steam 成就文本外，几乎没有别的可汉化 UI 文本** —— 而 Steam 成就**不值得汉化**（见 §4）。
**菜单项文字的真实来源至今未定位**，这是 UI 汉化的唯一真正卡点（见 §5）。

## 2. 已验证：exe 内 UTF-16 日文 = Steam 成就

用 `docs/data/steam-achievements.ja.txt`（33 个成就 = 66 条名称/描述）作基准对账：

| 分组 | 条数 |
|------|------|
| Steam 成就文本（名称 + 描述） | **66** |
| ├ exe 中已提取到 | **64（97%）** ✅ |
| └ 未提取到 | 2（`久遠院美術館`、`外道淫` —— 纯汉字无假名，被提取器的「含假名」判据滤掉，内容已由 Steam 清单确认） |
| **非成就的其他 exe 文本** | 50 |
| ├ ASCII 资源名错位伪串 | 47（如 `楴汴彥敭畮た弱湯` = `title_menu_1_on`、`档牡彡慮敭た1` = `chara_name_1`） |
| └ 真文本 | **3**（见下） |

仅有的 3 条非成就真文本：

```
0xD9A9A8  月英学園の全てを知る事ができた     ← 成就描述变体
0xDA3F88  月英学園 -kou-セーブデータ          ← 存档文件名
0xDA3FAC  月英学園 -kou-リプレイデータ        ← 回放数据文件名
```

字体相关格式串确认存在：`実績を解放！No.%d「%ls」`（成就解锁提示，成就名走 `%ls` 参数）。

### 提取方法（可复现）

判据四层，缺一层就出误报（都实测过）：

1. 只扫 `.rdata` 尾段（实测 0xCE0000–0xDD0000 密度最高，日文串集中在 0xD9A000–0xD9B000）；
2. 前后 NUL 终止（C 字符串）；
3. 含假名 + **假名占比 ≥ 12%** —— ASCII 串两两组合会"看起来像"日文，这类伪串汉字多假名少；
4. **位置聚类**：真实文本表成片存放（间距 < 64 字节），孤立的伪串丢弃。

⚠️ 试过但不可用：用「同偏移的 ASCII 连续可打印长度」判真伪 —— 日文 UTF-16 的低字节常落在
ASCII 可打印区（如 U+5168「全」= `68 51`），会误杀真串。
⚠️ 放宽起点判据（不要求前两字节为 NUL）会让结果从 114 条涨到 185 条并混入大量伪串。

## 4. Steam 成就：**不建议汉化**

理由（技术 + 收益）：

1. **Steam 客户端界面的成就文本来自 Steamworks 后台配置**，不是 `Getsuei.exe`。改 exe 对 Steam
   界面**完全无效**；而我们没有 Steamworks 上传本地化的权限。
2. 游戏内虽有解锁提示（`実績を解放！No.%d「%ls」`），但**外层提示语本身也是日文**。只翻成就名
   会让"日文框架 + 中文名字"更割裂。
3. 改 exe 属高风险操作（等长替换、可能触发校验），而 33 个成就是锦上添花，不影响游戏可玩性。
4. 即使改了，**Steam 界面与游戏内会不一致**（一边日文一边中文）。

⇒ **一律不动**。等将来若拿到 Steamworks 权限，走后台本地化配置才是正路。

### v1 测试：只改 `title_menu_00.hip`（菜单第一项）→ **未生效**

用户实机截图显示「はじめから」仍是正常日文。为排除工具链问题，本地做了两项无损性验证：

| 验证 | 方法 | 结果 |

### 排查中发现的另一条线索（重要）

全盘搜索（160+ pac 递归展开）确认：**`title_menu_00.hip` 在整个游戏里只有一处**
（`AE/title/UI_02_title.pac/tex.pac`）。但 `Getsuei.exe` 里的**资源名字池**（0xD911C8 附近）写的是：

```
getuei_title_rogo
title_menu_01_on / title_menu_01_off
title_menu_02_on / title_menu_02_off
...
title_menu_09_on / title_menu_09_off
Trademark
title_menu_mark_01 / title_menu_mark_02
```

而 pac 里的命名是 `title_menu_00/01/10/11/20/21...70/71`。**两套命名对不上**，
且 exe 用的那套名字（`title_menu_01_on.hip` 等）**在全部 pac 里都搜不到（0 处）**。

而 `UI_02_title.pac` 这个 pac 名在 exe 的 pac 名池里**确实存在**（0xCE3D40 附近：
`…UI_00_key_help.pac  UI_02_title.pac  options_screen.pac  system_menu.pac…`），
目录名池里也有 `AE/`、`title/`（0xCE4688 附近）。

⇒ 两种解释：
- **① 游戏未重启**：替换磁盘文件后，运行中的游戏实例不会重新加载（最可能）；
- **② 资源名映射**：exe 的 `_on/_off` 名字经某种映射指向 pac 内的 `_00/_01` 文件，
  或那套名字是旧版本残留的死代码。

### 规格与踩过的坑

- 配色实测：`off` = 白字 `(254,255,255)` + 黑描边 3px；`on` = 红字 `(225,12,37)` + 白描边 2.5px。
- 字体：**华康新综艺**（6 款对比后最接近原图的粗笔圆润手写感，且与已验收的台词图统一）。
- ⚠️ **画布尺寸必须逐张取原图**：`on`/`off` 尺寸并不相同（如 `_06_off`=256×64 而 `_06_on`=48×40），
  写死会溢出或错位。
- ✅ **画布尺寸可以改**（实测依据）：同一项 `off`/`on` 画布本就差异巨大
  （`_06_off`=256×64 vs `_06_on`=48×40），且各图**文字墨迹中心都正好落在画布正中**
  （`_06_off` ink 中心 (128,32) = 画布中心；`_09_off` 同）⇒ **游戏按画布中心定位**，
  与画布尺寸无关。改宽画布后**必须同步写 TgaImage 的 `Width`**，否则索引错位会花屏。
- ⚠️ **字高要按界面统一，不能照抄逐张原图**（实机二次反馈后修正）：原图 off/on 与各项之间
  本就有 33~51 的杂乱差异（`_01_off`=34 / `_01_on`=37，`_06`~`_09` 两态差 11~17px），
  假名混排时看不出来，**全汉字后就明显"大小不一"**。现按界面统一：01~05 用 36px、06~09 用 47px，
  宽度不足的（`_04` 开放之间需要 154px 而原画布 136px）**加宽画布**而不是缩字号。
- ⚠️ **版式位置照抄原图墨迹中心**'（2026-10-19 实机反馈「不居中/字号不统一/重叠」后修正）：
  原图各项**字高本来就不统一**（01=34、02/03/05=37、04=33、06~09=47）且一律居中于各自画布。
  正确做法：测出原图墨迹 `inkBbox`，让中文墨迹**中心对齐同一中心、字高等于原墨迹高**；
  若按"固定字高 + 画布居中 + 宽度约束"渲染，会出现字号被宽度二次压缩、与相邻项错位重叠。
- ⚠️ **TGA 写入要按原图 `Desc` 决定是否翻转 Y**'：`Desc bit5 = 0` 表示首行是图像底行，
  不翻转会得到上下颠倒的中文。
- ⚠️ 字号迭代必须用 `GraphicsPath.GetBounds()` 量字形实际尺寸，`MeasureString` 含行距会偏大导致溢出画布。
- 编码：以**原图的 TgaImage 为模板**，只替换 `Palette` 与 `Indices`，保留 Id/Desc/Origin/页脚等全部字段。

## 10. 菜单图最终参数（2026-10-19 第七次迭代定稿）

经过 7 轮实机反馈，最终确定三条硬规则：

### ① 画布尺寸一律不改

游戏按**固定行距**排版，不按画布中心定位。把 `_01` 从原高 40 改成 48 会把"从头开始"
下移 8px、与"继续游戏"紧贴（对照日文版可明显看出）；缩小 `_06~_09` 的 256×64 大画布
会让整个子菜单错位。

### ② 字高统一 32px，瓶颈是 40 高画布

`_01`/`_05`/`_06_on`等画布只有 **40 高**，是全场最紧的约束：
32（字身）+ 3（描边）= 35，居中还留 2.5px。故全场统一 **32px**。

### ③ 宽度不够用横向压缩，换字体无效

中文方块字比日文假名宽（假名「戻る」宽/字高 ≈ 0.75，汉字 ≈ 1.03）。实测 7 款中文字体
（等线/微软雅黑/华文细黑/黑体…）**宽/高比全是 1.01~1.06** —— 细字体只改笔画粗细，
不改字宽。正确做法是 `Matrix` 横向压缩。

⚠️ **GDI+ 矩阵坑**：不能把 `Translate` 和缩放合进同一个矩阵再 `Transform` ——
缩放会连带平移量一起缩放，压缩量算错。必须**两次 `Transform`**，第二次以画布中心缩放：

```fsharp
path.Transform mtx                                    // 先居中
use sm = new Matrix()
sm.Translate(-cx, -cy)                                // 移到原点
sm.Scale(scaleX, 1.0f, MatrixOrder.Append)
sm.Translate(cx, cy, MatrixOrder.Append)              // 移回
path.Transform sm
```

另注：`Matrix` **没有 `ScaleAt` 方法**，需用上面三段式实现"以某点为中心缩放"。

脚本：`scripts/remake-title-menu.fsx`（**从 `work/backup/story/image-menu/` 读原图**，
不能读游戏目录 —— 那里已被自己的产物覆盖，尺寸会一路漂移）。
## 11. 最终定稿：居中 + 统一 32px（2026-10-19，覆盖 §10 前两条）

§10 写的「照抄原图逐项字高」是错的，现修正：

### 原图字高参差是日文混排的取舍

原图各项墨迹高 34/37/35/31/33 并不统一，原以为是美术逐项微调。但日文版是
**汉字 + 假名混排**（はじめから、オプション），假名小、汉字大，美术为了整行视觉平衡
才对每项做了不同字号。**中文全是等宽方块汉字，没有这个问题** —— 照抄反而把
"为了迁就假名"的取舍继承下来了，所以看起来"字号奇怪"。

⇒ **中文环境应统一字号**。定稿 **32px**（40 高画布是瓶颈：32 + 描边 3 = 35，居中留 2.5px）。

### 坐标表 X/Y 是「图片中心」❌ **已作废（2026-10-19 见 §13）**

> ❌ 本节这条推论来自 Hex-Rays 的参数错位误读（`a7=128` 其实是 `a6`）。
> 汇编级复核结论：**`a7 = 0`，引擎不做居中补偿**，详见 `docs/re-notes.md`
> 与本文 §13。「文字居中于画布」因此**不是**引擎要求，而是当轮的近似做法。

IDA 见 `docs/re-notes.md`：`sub_53B400` 用固定坐标表 X 恒 512、Y = 320/400/480/560（间隔 80），
绘制缩放恒 1.0。判定 X/Y 是**图片中心**的证据：原图 `_06_off`（画布 256 宽）文字墨迹中心恰在
128，`_06_on`（画布 48 宽）中心恰在 24 —— 两张图尺寸差 5 倍，文字都落在各自画布正中，
只有"按图片中心定位"才能让 off/on 切换时文字不跳位。

⇒ 只要**文字居中于画布**，屏幕位置自动对齐 512 / 各行中心线，与画布尺寸无关。

### 因此三条规则（最终版）

1. 画布尺寸**保持原样**（不改）。
2. 文字**居中于画布**（不是左上角、不是按比例）。
3. 字高**全场统一 32px**；宽度超出画布时以中心为基准**横向压缩**（字高不变）。

曾经试错的三种策略（都错）：按原图逐项字高（中文显参差）、按画布比例 0.78、
左上角对齐原图墨迹（子菜单错位）。
## 12. 2026-10-19 收尾：两个未解问题（只分析，未改）

### 「开放之间」屏幕偏左

- **文件侧已验证居中**：`_04_off` 墨迹 `(3,7)-(133,41)`，画布 136×48 → 左右边距 3/2

- **矛盾点**：若上述都成立，屏幕上不该偏左
- **最可疑处**：`sub_5073B0` 调用传了 17 个参数，而函数签名只有 16 个（`a4` 是 `__int64` 占两槽）。
  参数映射可能整体错位一位 —— 若 `a8`（缩放 X）实际是 `0` 而非 `1.0f`，
  则 `v41 = 宽 × 0 = 0`、`x -= 0`，等于**左上角定位**，"居中"这个前提就要推翻。

### 子菜单 on/off 垂直位移（浩、返回）

- **文件侧已验证**：`_06_off`（256×64）与 `_06_on`（48×40）文字都居中，中心偏差均 +0.5px
- **现象**：切到 on 态时文字下移几像素（实机用辅助线确认）
- **最可疑处**：`v18 = (*(...+28))(v42)` 取的"高度"是**纹理尺寸**还是**显示尺寸**？
  若引擎对纹理做对齐/padding，`y -= 高×0.5` 用的就不是实际绘制高度，
  两张不同尺寸的图会得到不同的偏差量 —— 正好符合"偏几像素"的现象。

两问的验证入口相同：`sub_507770(a1, 0)` 返回对象的 `+24`（宽）/`+28`（高）语义。
